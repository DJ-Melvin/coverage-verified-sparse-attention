# Reproducibility Guide

This guide maps every figure and table in the paper to the command that
produces it. Table and figure numbers follow the camera-ready version.

`results/` ships only the inputs of the paper's figures, so every figure can be
redrawn without a GPU. All other results are produced by the launchers in
`scripts/`, which write to the files named in the tables below: `results/` for
the experiments of the submitted version and `results/camera_ready/` for those
added in the camera-ready version.

## Setup

- **Hardware.** 7B quality runs use one NVIDIA H100 (80 GB); the 70B runs
  use four H200 (141 GB). Long-context throughput uses H200; the hardware for
  each latency number is stated in its table caption.
- **Environment.** Python 3.10 with the versions pinned in
  `requirements.txt` (install torch, triton and flashinfer builds that match
  your CUDA driver), and the repository root on `PYTHONPATH`. `rouge_score`
  and `fuzzywuzzy` are required: without them the LongBench metrics silently
  fall back to token F1 and difflib.
- **Launchers.** `scripts/run_*.sh` are Slurm templates. Set
  `#SBATCH --account`, the partition, and `ENV_BIN` / `HF_HOME` for your
  cluster. In older launchers, also replace `cd /path/to/cvsa` and
  `/path/to/env/bin` with your actual paths. Submit from the repository root
  and run `mkdir -p logs` before `sbatch` so Slurm can open its log files.
  The launchers added for the camera-ready version take overrides as
  environment variables (`METHODS`, `TASKS`, `MAX_SAMPLES`, `OUT`, ...), e.g.
  `MAX_SAMPLES=5 TASKS=hotpotqa OUT=results/smoke_fixed_llama.json sbatch scripts/run_fixed_budget_noverify.sh llama`
  for a smoke test.
- **Data.** LongBench and MATH-500 are downloaded through Hugging Face
  `datasets`; RULER prompts are generated by `eval/ruler_cvsa.py`.
- **Decoding.** All LongBench and RULER runs use greedy decoding, so results
  are deterministic given the weights and inputs. LongBench point estimates use
  the first 50 samples of each task unless a caption says otherwise.
  Throughput numbers are median decode-step latencies over the timed steps of each run.
- **Main configuration.** CVSA-c4 is `cvsa_5_90_c4_ar20_dL0`: 5% base budget,
  `tau = 0.90`, page scoring and the coverage check every `M = 4` steps,
  recovery to 20%, layer 0 dense. The 70B runs use `M = 2` (`ar20_c2_dL0`).
- **Method names.** `ssa_` is accepted as an alias of `cvsa_`; several stored
  result files key the method by its `ssa_` spelling, and the launchers whose
  outputs are shipped in `results/` keep that spelling so the keys match.

LongBench outputs store per-task scores, per-sample scores and predictions, and
the backend's counters (`cvsa_stats`: pages attended, accept and re-score
counts) from which effective read is computed.

`eval/longbench_cvsa.py` checks an existing output's model, block size,
sample count, tasks, methods and sampling settings before resuming. Use a
different `--output` (or launcher `OUT`) when changing these settings,
including when moving from a smoke test to a full run. Historical outputs
without sampling fields use the original greedy defaults. Failed cells are
saved immediately and retried when the same command is rerun. Outputs include
completion counts and a `status` field; an incomplete run returns a nonzero
exit code and does not print a full-benchmark mean for an incomplete method.

### Rebuilding bootstrap intervals from new runs

`scripts/run_bootstrap_data.sh` collects the Mistral and Qwen inputs. The
Llama input uses the following recorded configuration (16 tasks, 100 samples
per task); run it in the same GPU environment from the repository root:

```bash
python eval/longbench_cvsa.py \
  --model meta-llama/Meta-Llama-3.1-8B-Instruct \
  --methods dense,fixed_10,ssa_5_90_c4_ar20_dL0,ssa_5_90_c8_ar20_dL0 \
  --max-samples 100 \
  --output results/longctx_quality_llama.json
```

Once all three runs are complete, move `results/pareto_bootstrap_cache.json`
to a backup outside `results/`, then run `python eval/plot_pareto.py`. The
script computes intervals from the new per-sample results only when that
cache is absent. This updates the cache and `paper/figures/pareto_frontier.*`;
retain the shipped files when you only want to redraw the paper's figure.
Other diagnostic plots likewise prefer their summary files, so regenerate
the corresponding summary after rerunning their source experiments.

## Twilight

The audit in Table 29 runs the official implementation:

```bash
git clone --recursive https://github.com/tsinghua-ideal/Twilight
git -C Twilight checkout ce6c050d63907840cb49df64200aad901dd7ea76
git -C Twilight submodule update
git -C Twilight apply "$PWD/scripts/twilight_pred.patch"
cp scripts/twilight_config_dense.json Twilight/benchmark/configs/config_dense.json
export TWILIGHT_ROOT=$PWD/Twilight MODELPATH=/path/to/Meta-Llama-3.1-8B-Instruct
TASKS="<16 LongBench tasks>" sbatch scripts/run_twilight_longbench.sh                       # sparse arm
TASKS="<16 LongBench tasks>" ALGO_CONFIG=configs/config_dense.json sbatch scripts/run_twilight_longbench.sh  # dense arm
```

Twilight runs in its own environment (our run: torch 2.5.0,
transformers 4.45.2, flashinfer-python 0.2.0.post1, flash-attn 2.7.4.post1).
The sparse arm uses Twilight's released `configs/config_quest_twi.json`
unchanged. `scripts/twilight_pred.patch` touches only Twilight's LongBench
harness: it caps the samples per task, fixes a decoding branch that crashed
on samsum and narrativeqa, and keeps only the last-position logits at
prefill. Realized coverage is Twilight's own `score_sum` field, recorded per
generation in its prediction files.
